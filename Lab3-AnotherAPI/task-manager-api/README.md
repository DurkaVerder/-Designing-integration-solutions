# Task Manager API

REST API для системы управления проектами и задачами.

Проект разработан в рамках лабораторных работ по проектированию и реализации REST API. В проекте реализованы CRUD-операции, JWT-аутентификация, версионирование API, идемпотентность, ограничение частоты запросов, пагинация, фильтрация, опциональное включение связанных данных, внутренний API и документация OpenAPI/Swagger.

---

# 1. Описание проекта

**Task Manager API** — серверное приложение для управления проектами и задачами пользователей.

API предоставляет возможность:

* регистрировать пользователей;
* выполнять аутентификацию;
* получать JWT-токен;
* создавать и управлять проектами;
* создавать и управлять задачами;
* назначать задачи пользователям;
* задавать статус и приоритет задач;
* устанавливать срок выполнения;
* получать информацию о просроченных задачах;
* фильтровать задачи по статусу и приоритету;
* использовать несколько версий API;
* использовать пагинацию;
* запрашивать дополнительные связанные данные через параметр `include`;
* предотвращать дублирование ресурсов при повторной отправке POST-запросов;
* ограничивать частоту запросов;
* использовать внутренний API для получения статистики;
* работать с API через интерактивную документацию Swagger.

# 2. Предметная область

Основная предметная область проекта — **система управления задачами**.

В системе используются основные сущности:

```text
User
 │
 ├──────────────┐
 │              │
 ▼              ▼
Project        Task
 │              ▲
 │              │
 └──────────────┘
```

## User

Пользователь системы.

Основные поля:

| Поле            | Тип      | Описание                 |
| --------------- | -------- | ------------------------ |
| `id`            | integer  | Уникальный идентификатор |
| `username`      | string   | Имя пользователя         |
| `email`         | string   | Электронная почта        |
| `password_hash` | string   | Хеш пароля               |
| `created_at`    | datetime | Дата регистрации         |

## Project

Проект пользователя, содержащий набор задач.

| Поле          | Тип      | Описание                 |
| ------------- | -------- | ------------------------ |
| `id`          | integer  | Уникальный идентификатор |
| `name`        | string   | Название проекта         |
| `description` | string   | Описание проекта         |
| `owner_id`    | integer  | Владелец проекта         |
| `created_at`  | datetime | Дата создания            |

## Task

Задача, принадлежащая определённому проекту.

| Поле          | Тип      | Описание                 |
| ------------- | -------- | ------------------------ |
| `id`          | integer  | Уникальный идентификатор |
| `project_id`  | integer  | Проект задачи            |
| `title`       | string   | Название задачи          |
| `description` | string   | Описание                 |
| `status`      | string   | Статус                   |
| `priority`    | string   | Приоритет                |
| `assignee_id` | integer  | Назначенный пользователь |
| `created_at`  | datetime | Дата создания            |
| `due_date`    | datetime | Срок выполнения          |

Допустимые статусы:

```text
todo
in_progress
done
```

Допустимые приоритеты:

```text
low
medium
high
```

# 3. Связи между сущностями

В системе реализованы следующие связи:

* один пользователь может владеть несколькими проектами;
* один проект может содержать несколько задач;
* каждая задача относится к одному проекту;
* задача может быть назначена пользователю.

Схематично:

```text
User 1 ───────── N Project
                     │
                     │ 1
                     │
                     N
                   Task
                     │
                     │
                     ▼
                   User
```

# 11. Аутентификация

Для защиты пользовательских endpoint'ов используется **JWT-аутентификация**.

Общий сценарий:

```text
Регистрация
     │
     ▼
POST /api/v1/auth/register
     │
     ▼
Авторизация
     │
     ▼
POST /api/v1/auth/login
     │
     ▼
JWT access token
     │
     ▼
Authorization: Bearer <token>
     │
     ▼
Защищённые endpoint'ы
```

## Регистрация

```http
POST /api/v1/auth/register
```

Пример запроса:

```json
{
  "username": "alex",
  "email": "alex@example.com",
  "password": "12345678"
}
```

Пароль пользователя не хранится в базе данных в открытом виде.

Для хранения используется хеширование Argon2.

## Авторизация

```http
POST /api/v1/auth/login
```

Пример ответа:

```json
{
  "access_token": "eyJ...",
  "token_type": "bearer"
}
```

Полученный токен передаётся в заголовке:

```http
Authorization: Bearer <access_token>
```

# 13. CRUD-операции

Для основных ресурсов реализован стандартный CRUD:

```text
Create → POST
Read   → GET
Update → PUT
Delete → DELETE
```

Например, для задач:

```text
POST   /api/v1/tasks/
GET    /api/v1/tasks/
GET    /api/v1/tasks/{task_id}
PUT    /api/v1/tasks/{task_id}
DELETE /api/v1/tasks/{task_id}
```

Структура URL использует имена ресурсов во множественном числе, что делает API предсказуемым и единообразным.

# 16. API V2

Вторая версия API предназначена для расширения функциональности работы с задачами.

Она доступна через:

```text
/api/v2/tasks/
```

Главная задача V2 — расширить существующий API без нарушения работы V1.

В V2 реализованы:

* `is_overdue`;
* `days_until_due`;
* фильтрация по статусу;
* фильтрация по приоритету;
* пагинация;
* параметр `include`;
* дополнительные сведения о проекте и исполнителе;
* идемпотентность создания задачи через `Idempotency-Key`.

---

# 17. Отличия V2 от V1

## 17.1. Поле `is_overdue`

V2 автоматически определяет, просрочена ли задача.

Пример:

```json
{
  "id": 10,
  "title": "Подготовить отчёт",
  "status": "in_progress",
  "due_date": "2026-09-15T18:00:00",
  "is_overdue": true
}
```

Поле не хранится отдельно в базе данных.

Оно вычисляется сервером на основе:

* текущего времени;
* `due_date`;
* текущего статуса задачи.

Выполненная задача со статусом `done` не считается просроченной.

## 17.2. Поле `days_until_due`

V2 также возвращает количество дней до наступления срока.

Пример:

```json
{
  "is_overdue": false,
  "days_until_due": 5
}
```

Если срок уже прошёл:

```json
{
  "is_overdue": true,
  "days_until_due": -3
}
```

Если `due_date` отсутствует:

```json
{
  "is_overdue": false,
  "days_until_due": null
}
```

# 18. Фильтрация задач в V2

В V2 реализована фильтрация с помощью query-параметров.

## Фильтрация по статусу

```http
GET /api/v2/tasks/?status=in_progress
```

Допустимые значения:

```text
todo
in_progress
done
```

## Фильтрация по приоритету

```http
GET /api/v2/tasks/?priority=high
```

Допустимые значения:

```text
low
medium
high
```

## Комбинированная фильтрация

```http
GET /api/v2/tasks/?status=in_progress&priority=high
```

В этом случае API возвращает задачи, которые одновременно соответствуют указанному статусу и приоритету.

# 19. Пагинация

Для получения списка задач в V2 реализована пагинация.

Используются параметры:

* `page` — номер страницы;
* `limit` — количество элементов на странице.

Пример:

```http
GET /api/v2/tasks/?page=1&limit=10
```

Допустимый диапазон:

```text
page  >= 1
1 <= limit <= 100
```

Пример ответа:

```json
{
  "items": [
    {
      "id": 1,
      "project_id": 1,
      "title": "Разработать API",
      "description": "Реализовать CRUD",
      "status": "in_progress",
      "priority": "high",
      "assignee_id": 1,
      "created_at": "2026-09-19T12:00:00",
      "due_date": "2026-09-25T18:00:00",
      "is_overdue": false,
      "days_until_due": 5
    }
  ],
  "page": 1,
  "limit": 10,
  "total": 25,
  "pages": 3
}
```

Пагинация позволяет не загружать все задачи пользователя одним запросом.

В проекте выбран простой подход `page` + `limit`, так как он удобен для реализации постраничного отображения данных и хорошо подходит для учебного REST API.

# 20. Опциональные данные через `include`

V2 поддерживает query-параметр `include`.

Он позволяет клиенту запросить дополнительные связанные данные.

Доступные значения:

```text
project
assignee
```

## Только основные данные

```http
GET /api/v2/tasks/
```

## Включить проект

```http
GET /api/v2/tasks/?include=project
```

## Включить исполнителя

```http
GET /api/v2/tasks/?include=assignee
```

## Включить оба объекта

```http
GET /api/v2/tasks/?include=project,assignee
```

Пример ответа:

```json
{
  "id": 2,
  "project_id": 4,
  "title": "Разработать API",
  "description": "Реализовать CRUD",
  "status": "todo",
  "priority": "medium",
  "assignee_id": 3,
  "created_at": "2026-09-18T16:07:00.256329",
  "due_date": "2026-09-18T19:04:19.481000",
  "is_overdue": true,
  "days_until_due": -7,
  "project": {
    "id": 4,
    "name": "Проект"
  },
  "assignee": {
    "id": 3,
    "username": "alex"
  }
}
```

`include` является необязательным параметром.

Если клиенту не нужны связанные данные, они не добавляются в ответ. Это позволяет управлять составом ответа API.

# 22. Версионирование API

Для версионирования используется URL-префикс:

```text
/api/v1/
/api/v2/
```

V1 и V2 работают независимо.

Существующий клиент может продолжать использовать:

```text
/api/v1/tasks/
```

а новый клиент может использовать:

```text
/api/v2/tasks/
```

Такой подход позволяет добавлять новые возможности без изменения существующего интерфейса V1.

---

# 23. Обратная совместимость

При разработке V2 учитывалось требование обратной совместимости.

Существующие endpoint'ы V1 не были удалены или переименованы.

Новые возможности добавлены в:

```text
/api/v2/
```

и:

```text
/api/internal/
```

Поэтому клиент, использующий V1, продолжает работать с прежним набором endpoint'ов.

К breaking changes относятся, например:

* изменение существующего URL;
* удаление поля из ответа;
* изменение типа существующего поля;
* изменение обязательности существующего параметра;
* изменение смысла уже существующего поля.

Добавление нового необязательного параметра или отдельной версии API не требует изменения существующих клиентов.

# 24. Идемпотентность

В проекте реализована поддержка идемпотентных POST-запросов с помощью заголовка:

```http
Idempotency-Key: <unique-key>
```

Механизм применяется при создании ресурсов.

Например:

```http
POST /api/v1/projects/

Idempotency-Key: project-001
```

А также при создании задачи через V2:

```http
POST /api/v2/tasks/

Idempotency-Key: task-001
```

При первом запросе сервер создаёт ресурс и сохраняет результат выполнения.

Если клиент повторяет запрос с тем же ключом для того же endpoint, сервер возвращает ранее сохранённый результат вместо повторного создания ресурса.

Для хранения данных используется таблица:

```text
idempotency_records
```

В ней сохраняются:

* ключ идемпотентности;
* endpoint;
* HTTP-статус результата;
* тело ответа;
* время создания записи.

Механизм позволяет защитить API от появления дубликатов при повторной отправке POST-запросов.

Типичные причины повторной отправки:

* сетевая ошибка;
* потеря ответа сервера;
* повторная отправка формы;
* временный сбой соединения.

# 25. Rate Limiting

Для API реализовано ограничение частоты запросов.

Текущие параметры:

```text
Лимит: 10 запросов
Временное окно: 60 секунд
Идентификатор клиента: IP-адрес
```

Ограничение применяется ко всем endpoint'ам с префиксом:

```text
/api/
```

включая пользовательские, V2 и внутренние endpoint'ы.

После каждого успешного запроса сервер возвращает:

```http
X-Limit-Remaining: 8
```

Значение показывает количество оставшихся запросов в текущем временном окне.

После превышения лимита сервер возвращает:

```http
429 Too Many Requests
```

и:

```http
X-Limit-Remaining: 0
Retry-After: 42
```

`Retry-After` показывает количество секунд до возможности повторить запрос.

# 26. Внутренний API

Для внутренних сервисов и административных задач реализован отдельный API.

Префикс:

```text
/api/internal/
```

Основной endpoint:

```http
GET /api/internal/tasks/statistics
```

Endpoint возвращает общую статистику по задачам:

```json
{
  "total": 10,
  "todo": 4,
  "in_progress": 3,
  "done": 3,
  "overdue": 2
}
```

Статистика включает:

* общее количество задач;
* количество задач со статусом `todo`;
* количество задач со статусом `in_progress`;
* количество выполненных задач;
* количество просроченных задач.

## Защита внутреннего API

Внутренние endpoint'ы защищены отдельным API-ключом.

Клиент должен передать заголовок:

```http
X-Internal-Key: <internal-api-key>
```

При отсутствии или неправильном ключе API возвращает:

```text
403 Forbidden
```

В отличие от пользовательских endpoint'ов, для внутреннего endpoint'а используется отдельная схема авторизации через API Key.

Внутренний API предназначен для:

* административной панели;
* внутренних сервисов;
* мониторинга;
* получения агрегированной статистики.

На внутренний API также распространяется общее ограничение частоты запросов.

# 28. Идемпотентность HTTP-методов

В проекте учитывается назначение HTTP-методов:

```text
GET    → получение данных
POST   → создание ресурса
PUT    → изменение ресурса
DELETE → удаление ресурса
```

`GET`, `PUT` и `DELETE` используются для операций, которые должны иметь предсказуемый результат при повторении.

`POST` обычно используется для создания нового ресурса и может приводить к созданию нескольких ресурсов при повторной отправке.

Поэтому для POST-операций создания в проекте реализован механизм:

```text
Idempotency-Key
```

Он позволяет повторно отправить запрос без создания дубликата.
